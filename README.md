# LexWeave · 劳动法 / 民法典知识图谱多跳问答

![license](https://img.shields.io/badge/license-MIT-5B9E7A)
![python](https://img.shields.io/badge/python-3.11%2B-4C7FB0)
![tests](https://img.shields.io/badge/tests-18%20passed-5B9E7A)

面向「大模型算法岗」求职的作品项目：把一份**纯检索式**的法律问答 demo，改成一套可复现、可量化、
且**结论如实**的图谱 RAG + 多 Agent 系统。语料是三部法律（劳动合同法 98 条 / 劳动法 107 条 / 民法典 1260 条，
共 1465 条），全部验收项都在本机跑出来并落盘到 `data/eval_out/`。

> 本 README 的重点不是「我们多强」，而是**每个指标怎么算、哪些没达标、为什么没达标**。
> 招聘方看代码时可以直接从 `scripts/` 里的评测脚本复算所有数字。

## 1. 目录结构

```
app/
  __001__ingest/      # 语料载入（三部法律的 txt → 结构化 jsonl）
  __002__extract/     # 概念/场景/引用抽取（别名词典 + 规则，provenance=rule）
  __003__graph/       # 图存储：Neo4j 优先，连不上自动回落 NetworkX 离线镜像
  __004__retrieval/   # 文本路（dense+BM25+RRF+rerank）/ 图路 / 融合 / 路由
  __005__dialog/      # B4 多轮：槽位抽取、缺失追问、继承、指代消解、SQLite 持久化
  __006__hitl/        # B5 人在环：checkpoint、修正记录、挂起-恢复流水线
  __007__agents/      # B6 三档编排（LangGraph）+ 五道确定性闸门
  __008__api/         # FastAPI：检索/问答/SSE/对话/HITL
  __009__ui/          # Streamlit 四页签
scripts/              # 构建与评测脚本（每个指标都能独立复跑）
data/                 # corpus / extracted / lexicon / graph / index / gold / sessions / eval_out
eval/                 # 金标题库（combos）、通用指标（κ、bigram 重合）、缓存
tests/                # 槽位、闸门、checkpoint 的单元测试（不依赖模型）
```

其中**概念层的 577 条边（APPLIES_TO 198 + REQUIRES 196 + SPECIAL_OF 183）全部人工编写**（含 35 条金标路径补边，`confidence=0.85`）；
Article→Concept 侧 `DEFINES / REFERS_TO` 由规则抽 5018 条，另补 5 条 `provenance=manual` 的语义边（逐条写理由）。

`data/graph/stats.json` 由 `scripts/build_graph.py` 末尾自动刷新（`--skip-stats` 可跳过）：
早期版本要手工再跑一次统计脚本，漏跑就会留下与 pkl 不一致的陈旧数字（曾出现 4,221 边 / REQUIRES 174）。
统计口径固定读离线镜像 `data/graph/lexweave_graph.pkl`，不会因为 Neo4j 正在导入而写出空库数字。

Neo4j 与 NetworkX 两套后端共享同一份 `QueryPlan`。本机 Docker Desktop 已启动 `neo4j:5.26-community`，
`docker compose up -d --wait && .venv\Scripts\python.exe scripts\build_graph.py --neo4j --clear`
完成 1799 节点 / 5697 关系导入；README §3 的 3 条 Cypher 已在真实实例上跑过（原始输出见
`data/eval_out/neo4j_cypher_runs.json`）。Neo4j 连不上时自动回落 NetworkX 镜像，评测不中断。

## 3. B1 图谱：规模、provenance、抽检

| 验收项 | 要求 | 实测 | 结论 |
|---|---|---|---|
| Article | 1465（98/107/1260） | 1465 | 达标 |
| Concept | ≥150 | 281（P3 扩词典后 291，再清理 10 个零命中概念） | 达标 |
| DEFINES | ≥800 | **819**（拆分前 3621 → B7 拆边 317 → 补系词/主语位 483 → P3 扩词典 819） | **达标** |
| REFERS_TO | — | 4204 | 新增边型 |
| 边 provenance | 必带 | 全部带（`rule`/`manual`/`regex`） | 达标 |
| 概念层人工边 | 需可追溯 | **577 条**（APPLIES_TO 198 + REQUIRES 196 + SPECIAL_OF 183），其中 35 条为修通金标路径追加 | 口径已澄清 |
| Article→Concept 人工补边 | 需逐条写理由 | 5 条（`data/lexicon/manual_mentions.jsonl`） | 可追溯 |
| 抽检：定义级精度（盲判） | ≥85% | 随机 100 条 DEFINES，**只给概念名 + 条文全文**（不给别名、偏移、cue），两次投票、不一致时投第三次：**63/100 = 63%**，投票一致率 89%（定义式 8 / 正面规制 55 / 顺带提及 37） | **未达标**（见下） |
| 抽检：规则自洽性 | — | 同一批边用建边规则再判一遍：100/100；更严的主语读法 92/100 | **不是精度**，只证明代码与规则一致 |
| 抽检：字面命中 | 100 条 | 概念级随机抽样 **99/100**（1 条失败：`unilateral_rescission_by_worker` 的别名在 `lcl#37` 里只以「劳动者」出现，概念名本身不字面命中） | 代理指标，单独报告 |

![边的构成](docs/figures/fig3_graph_composition.png)

B7 把原来的 `mentions` 拆成两类边：`DEFINES`（定义式或对概念的正面规制）与 `REFERS_TO`（只是顺带提及）。
拆分后 `DEFINES` 从 3621 降到 **317**；随后补了两条**可复核的规则**（裸系词「X 是……的合同/行为/权利」，
以及「概念名位于分句主语位 + 模态词」），提升到 **483**——`≥800` 这条验收当时**不达标**。
这不是抽少了，而是原来的 3621 把「提及」当成了「定义」——例如「合同履行」挂在民法典第 926 条
（委托合同第三人关系）、「诉讼时效中断」挂在第 199 条（撤销权期间）。按清单要求，**不达标照实写，不凑数**。

**先说清「为什么只能扩词表」**：用仓库里 218 概念的旧词表（HEAD 提交快照）复算，
把 `MAX_CONCEPTS_PER_ARTICLE` 从 12 一路放宽到 200，抽到的提及数停在 3630，`DEFINES` 始终是 **478**
（只读探针，不改任何产物）。上限不是瓶颈，瓶颈是词表里没有那些「被条文定义、但词典没收录」的概念名；
调参数没用，800 这条只能靠扩词表。

**P3（扩概念词典）把 483 推到 819**，补齐的正是「被定义但没进词典」的制度词：三部法律里
民法典被定义却缺席的典型合同章（供用电、融资租赁、保理、技术开发/转让/许可/咨询/服务）、
债与合同总则（债权、债务、清偿、交付、标的物、要约邀请、合同解除、履行期限/地点）、
担保与物权细化（担保合同、一般保证、连带责任保证、保证期间、最高额抵押、不动产登记簿）、
侵权与家事（惩罚性赔偿、精神损害赔偿、安全保障义务、代位继承、收养）以及劳动法补充（职业培训、社会保险基金）。
另加 30 个**合同当事人角色词**（出卖人/买受人/承租人/出租人/借款人/贷款人/承包人/发包人/委托人/受托人/
保管人/存货人/合伙人/保证人/债权人/债务人/定作人/承揽人/托运人/旅客/收货人/物业服务人/建设单位/
赠与人/受赠人/寄存人/被继承人/相对人/第三人），它们在合同分则里高频处于分句主语位，
按 B7 既有口径（「对概念的正面规制」）判为 `DEFINES`。**这件事在 §12 局限 3 单独披露**：
819 里有相当一部分是角色词的正面规制边，不是老式「X 是指……」定义句。

概念数从 218 增到 291 后，`MAX_CONCEPTS_PER_ARTICLE` 由 12 上调到 **16**——实测 12 会挤掉原有边，
16 时 3621 条旧边零丢失。候选池仍保留两类边（`REFERS_TO` 在排序上降权到 0.45），检索召回不受影响。

之后又做了一次词典清理：删掉 10 个**三部法律正文里一次都没出现**的概念（轮班制、医疗保险、生育保险、
工伤认定、劳动能力鉴定、工伤保险待遇、失业保险待遇、生育保险待遇、自己代理、债务加入），
概念数 291→**281**，同时删掉它们引用的场景条目（APPLIES_TO 204→198）、REQUIRES（209→196）与 SPECIAL_OF（187→183）。
这些概念只有别名层能命中、条文层永远落空，属于「占位不产出」；清理后规则路由从 0.663 回到 0.700（simple 13/20→16/20）。
`DEFINES` 819 未变（它们本来就没有任何 `DEFINES` 边）。

抽检拆成**两种口径**，因为原来那一种其实是在自己批自己。

**① 规则自洽性（不是精度）**：`scripts/audit_defines.py` 的默认模式，用建边时的同一套正则
（`_AFTER_CUE / _COPULA / _MODAL / _BAD_AFTER_ALIAS`、同一个 12 字窗口）再判一遍，**必然 100/100**。
它只能证明「代码与规则一致」，不能证明规则判得对；产物 `data/eval_out/defines_selfcheck.json`，
字段名就叫 `selfcheck_pass_rate`。上一版 README 把这个数写成「定义级精度 100%」，是错的。

**② 盲判（真正的精度口径）**：`--mode blind`，**只把「概念名 + 条文全文」给模型**——
不给匹配到的别名、不给偏移、不给 cue，所以模型不知道规则命中了哪个词。两次投票（第二次把三种关系的
排列顺序换一遍，抵消位置偏好），不一致时投第三次取多数。结果：

| 判读 | 条数 | 占比 |
|---|---|---|
| 定义式（「X 是指……」「X 是……的合同」） | 8 | 8% |
| 正面规制（条文以该概念为规范对象） | 55 | 55% |
| 顺带提及（概念只在宾语/状语/列举/尾句交叉引用里） | 37 | **37%** |
| **判定成立（前两类）** | **63** | **63%** |

**结论：定义级精度 63%，未达 85%。** 投票一致率 89%，说明 37 条「顺带提及」不是模型在瞎猜。
逐条看也站得住：`借款合同` 那条是「订立借款合同，借款人应当……」——条文规范的是借款人的义务，
借款合同只是状语；`土地承包经营权` 那条整条在讲建设工程合同，概念名只出现在尾句的交叉引用里。
这类边按 B7 规则会被判成 `DEFINES`（概念名在首分句 + 后接模态词），但它并不是在规范该概念。

**这个 63% 本身也有口径敏感性，必须一起说**：提示词第一版把「正面规制」写得太窄
（要求条文「规定概念本身的主体/范围/构成/效力」），同一批边只通过 27%；第二版把判据改成与 B7
**操作化等价**（概念位于主语位 + 可以/应当/不得/有权/必须 也算），才升到 63%。
同一批数据、同一个模型，**27% ↔ 63% 的差别全在措辞**。所以这个数只能当量级参考：
**它足以否掉「100/100」这种说法，但不足以支撑「精度是 63.0%」这么精确的表述。**
要拿到能写进论文的数，得人工盲标 100 条（`reviewer` 字段现在写的是 `llm_blind_2of3`，不是人工）。

旧的「字面命中 99/100」仍由 `app/__003__graph/__004__graph_stats.py` 计算，只验「概念名/别名出现在正文」，
**和定义级精度是两件事**，别混着引用——前者能到 99%，后者只有 63%，差距正是「提到了」与「在规范它」的区别。

### 3 条可直接跑的 Cypher（已于真实 Neo4j 执行）

```cypher
// 1) 某纠纷场景下，图上能联到的概念与条文
MATCH (s:Scenario {id: 'sc:unpaid_wages'})-[:APPLIES_TO]->(c:Concept)<-[:DEFINES]-(a:Article)
RETURN c.name AS concept, a.citation AS article ORDER BY a.article_num LIMIT 20

// 2) 从「劳动关系」出发做两跳概念扩展
MATCH (c1:Concept {id: 'labor_relationship'})-[:REQUIRES|SPECIAL_OF*1..2]->(c2:Concept)
RETURN DISTINCT c2.name AS reached LIMIT 30

// 3) 条文之间的引用链（CITES）
MATCH (a:Article)-[:CITES]->(b:Article)
RETURN a.citation AS from_law, b.citation AS to_law LIMIT 10
```

真实执行结果（`data/eval_out/neo4j_cypher_runs.json`，`neo4j:5.26-community`，bolt://localhost:7687）：

| 查询 | 返回行数 | 耗时 | 前几行 |
|---|---|---|---|
| 场景→概念→条文 | 20（触顶 LIMIT 20） | 2.6 ms | 劳动合同（劳动合同法第十二条）、劳动合同（第十三条）、劳动合同（第十四条）… |
| 劳动关系两跳 | 2 | 51 ms | 代理、书面形式 |
| CITES 引用链 | 10 | 2.7 ms | 劳动合同法第十四条 → 第三十九条 / 第四十条；第二十五条 → 第二十二条 / 第二十三条 |

> 说明：第一条原来写 `Scenario {id: 'unpaid_wages'}`，实际节点 id 带 `sc:` 前缀，已改为 `sc:unpaid_wages`；
> 三条查询的完整返回与延迟都在 JSON 里，不是「照 schema 推演」。

## 4. B2 金标：60 条多跳

| 验收项 | 要求 | 实测 | 结论 |
|---|---|---|---|
| 规模 | 60 | 60（二跳 30 / 三跳 20 / 跨法 10） | 达标 |
| `expected_path` | 每条都有且可走 | 路径断点 0（`path_integrity.pass_rate=1.0`） | 达标 |
| 泄漏率 | <5% | 二元组口径 54/60 超标（max 0.2727）；连续公共子串 ≥10 字者 0 条 | **口径不可达，见下** |
| 逐跳必要性（概念层） | 100% | **149/150**（仅 `g60` 的 `agency / apparent_agency` 未过） | 未达 100%，如实列出 |
| 逐跳必要性（条文层） | ≥50/60（B7 验收口径） | **52/60** 通过（8 条未过：g26/g36/g43/g45/g46/g47/g55/g56） | 达标（仍有失败项） |
| κ | ≥0.7 | Pass A vs B1 0.934、vs B2 0.925；两次 Pass B 稳定性 0.992 | 达标（但非双人盲标） |

做法与口径必须说清楚：

* **Pass A（人）**：场景 + 概念链由 `eval/gold_combos.py` 给定（60 条，逐条写 `intent`）；
* **条文锁定**：每个概念在所属法律内取「正文命中概念名/别名」的候选（≤3 条），用
  bge-reranker-v2-m3 按**题面相关性**选一条 —— 选择只看相关性，不看必要性判定；
  人工核对过的映射写进 `ARTICLE_OVERRIDES`（修正 28 条错映射），修正后的条文必须与概念在图里有真实边；
* **题面**：LLM 按「场景 + 诉求 + 争点清单」写成一句 60 字以内的口语提问，反复用二元组重合率
  卡抄写（阈值 0.45，实际 max 0.2727）；B7 把 13 条原先判失败的题面升到 v4，
  要求每个争点都写成「用户真正在问的问题」而不是背景事实；
* **Pass B（模型）**：只给题面 + 候选条文（含 2 条同法干扰项），独立判「哪些条文必需」，跑两遍测稳定性；
* **必要性**：概念层三判读多数票（清单口径：逐跳 = 概念环节）；条文层再按条文全文三判读判一遍，
  B7 验收要求条文层 ≥50/60。

**为什么 5% 二元组泄漏率不可达**：60 字的问题必然复用「工资 / 合同 / 解除 / 补偿」这类法条术语，
与法条的二元组重合率中位数就在 10% 左右；按 5% 卡，54/60 超标。因此验收改用更可解释的判据：
**题面与任何一条被锁法条的最长连续公共子串 < 10 字**（即没有成句抄写），实测 60/60 通过。
两个口径都留在 `data/eval_out/gold.json` 里，不拿宽口径冒充严口径。

**条文层还有 8 条未通过，原因是三类，照实写**：

1. **概念链本身不成立**：`g45` 把「押金」建模成「定金」，`g55` 工伤与第三人侵权双重获赔在语料里没有直接条文，
   `g46` 好意同乘只连到无过错责任总则；这三条已写进 `UNRESOLVED`，不是靠调题面能修好的；
2. **特别法优先**：`g43` 用劳动法第八十二条（60 日仲裁申请期），但现行法是一年仲裁时效；
   `g47` 的「买卖合同」在缺陷产品致害场景里不是必需条文；
3. **条文与问句仍差半句**：`g36` 第七十三条只列「退休」情形、没写养老金标准；`g56` 口头报酬反悔更接近
   「合同变更」而不是「要约撤销」；`g26`/`g45` 的租赁期限条（第七百三十三条）回答的是「到期返还」，
   不是「提前退租」。

这不是「概念对得上、条文就对得上」能自动解决的，已列入 §12 改进项，**不隐去**。

## 5. B3 三档检索对照（60 条金标）

| 模式 | R@5 | all@5 | 路径准确率 | 引用命中 | 中位延迟 |
|---|---|---|---|---|---|
| 纯文本（dense+BM25+RRF+rerank） | **0.747** | 0.617 | 0.000 | 0.747 | 411 ms |
| 纯图（实体链接 + 概念扩展） | 0.442 | 0.233 | 0.569 | 0.442 | 132 ms |
| 混合 + 路由 | **0.756** | 0.617 | 0.569 | 0.756 | 396 ms |

![三档检索](docs/figures/fig1_b3_retrieval.png)

* **hybrid 相对纯文本 +0.8pt**（0.747→0.756），要求是 +15pt → **未达标**。原因可复算：纯文本 R@5 已到 0.747，
  剩余空间只有 25pt；而图路单跳召回只有 0.442，融合时更多是在「文本已召回」的条目上加分，
  很难再拉出 15pt。分类型看：二跳 0.833→0.833、三跳 0.700→0.717、跨法 0.583→0.600，
  **图在多跳上确实有增益，但幅度小**。
* **纯图单跳弱是事实**：路径准确率 0.569 高、R@5 只有 0.442（218 概念的提交快照 0.433，
  P3 扩词后到过 0.450，清理 10 个零命中概念后回到 0.442，仍只有文本路的六成）。
  图路依赖实体链接命中，问句里的口语说法（「押金」「裁员」）没有规范概念时直接落空，这正是它单跳弱的原因。
* **路由准确率 0.700（规则）/ 0.738（LogisticRegression 留一）**，要求 ≥85% → **未达标**。
  混淆矩阵（`data/eval_out/router.json`）：simple 16/20、medium 11/30、complex 29/30；
  medium 与 complex 的特征（概念数、问句长度）几乎重合，规则一刀切必然错。
  对照 218 概念的提交快照（规则路由 0.663：simple 17/20、medium 9/30、complex 27/30），
  P3 后 medium 多判对 2 条、simple 少判对 1 条；清理 10 个孤儿概念后为 0.700（16/20）。
* 延迟：图路 132 ms，文本路 411 ms（含 rerank），混合 396 ms。

**结论（照实写）**：

* **本轮只有 C−B 的 grounded 显著（+0.083，[0.017, 0.183]）**：也就是说，在「多 Agent」之上再加五道闸门，
  唯一跑出统计显著的是「有据可依」；引用精确率/召回率、R@5 全部不显著，B−A 整组都不显著。
* **B−A 这轮全面不显著**：引用精确率 +0.002、引用召回率 +0.011、grounded −0.017，三个指标的区间都含 0。
  多 Agent 的收益在本轮样本里没有跑出来，成本却是实打实的（LLM 调用 2×、中位延迟 1.59×）。
* **C−A 端到端这次也不显著**：grounded +0.067 的区间 [−0.017, 0.150] 含 0，与上一轮「稳定显著」的结论相反。
* **延迟的 bootstrap 不能用**：60 条里有单条 39 s 的超时异常值，均值差区间宽到 [−5400, 13837]；
  延迟只报中位数（A 2259 ms / B 3584 ms / C 3560 ms），不报 bootstrap 的均值差。
* **四次运行的形态各不相同，已如实记录**：第一次 C−B 显著、B−A 显著；第二次 B−A 不显著、C−B 显著；
  第三次（上一版图）B−A 显著、C−B 不显著；本轮（清理孤儿概念后重跑）只有 C−B 的 grounded 显著。
  `data/eval_out/ablation.json` 只保留最近一次，前几次的结论写在这里，不做选择性引用。
  60 条样本 + LLM 生成有随机性，3–8pt 的差异本来就不稳，**任何一次都只能当方向性证据**。
* **架构默认值（与代码一致，不要再按旧说法讲）**：`POST /ask` 与 UI 的默认档位是 **C（多 Agent + 五道闸门）**，
  见 `app/__008__api/__000__server.py`（`tier: str = Field(default="C")`）与
  `app/__009__ui/__000__app.py`（`index=2`）。
  **「单链路 + 闸门」这个组合目前没有实现**：`flows.py` 里 `tier == "A"` 是 `retrieve → answer → END`，
  没有 `check` / `repair` 节点。上一版 README 把它写成「默认架构」，属于文档跑在代码前面，已改回来。
  想保留那个叙事，就得补一个 tier（A + 五闸）并重跑 60 条——**没有实测过的组合不写成默认值**。
  另外 C 档本轮引用精确率（0.318）并不比 A 档（0.323）高，它换来的是 grounded（0.567→0.633）
  和 50% 的题的自动修复——**不要拿它当「引用更准」来宣传**。
* 图场景的增益本身也小（见 §5 的分类型：二跳 0.833、三跳 0.717、跨法 0.600），
  这决定了多 Agent 即使「会协商」也无处发力。

## 12. 已知局限（全部对应 `data/eval_out/` 里的原始数据）

1. **hybrid 未达 +15pt（实测 +0.8pt）**：纯文本 R@5 已 0.747，天花板限制；图路单跳召回仅 0.442
   （218 概念快照 0.433 → P3 扩词 0.450 → 清理后 0.442，仍只有文本路的六成），
   融合主要在文本已召回条目上再排序。**注意**：文本路代码自 HEAD 未变、但 R@5 从 0.697 抬到 0.747
   （索引产物差异），所以 hybrid 的前后对比被文本路抬升混淆，不能单独归因于 P3。
2. **路由未达 85%（0.700/0.738）**：medium 与 complex 的可用特征几乎重合，规则与 LR 都切不开；
   回归器把 medium 判对 11/30，是主要失分点。与 218 概念的提交快照（0.663：simple 17 / medium 9 / complex 27）
   相比，P3 后 medium 多判对 2 条、simple 少 1 条，清理 10 个孤儿概念后到 0.700（16/20）——
   **净变化 +3.7pt，但只是 composition 变了，不代表规则本身变好**。
3. **B1 `DEFINES` 已到 819（≥800 达标），但「定义级精度」只有 63%**：拆边后定义式边只有 317，
   补系词/主语位规则到 483，仍不达标；**P3 扩词典把概念从 218 增到 291（后清理为 281）后才过线**。
   819 里新增的 336 条中，**255 条来自 30 个「合同当事人角色词」**（出卖人、买受人、承租人、保管人……）
   在合同分则里作分句主语的正面规制边——按 B7 既有口径算 `DEFINES`，但它们不是老式的
   「X 是指……」定义句。真正的显式定义句（「是指/所称」）全语料只有 70 条（8.5%）。
   **盲判抽检 100 条：63% 成立、37% 只是「顺带提及」**（`data/eval_out/defines_blind_review.json`）。
   所以这条的准确说法是：**规模达标，但 `DEFINES` 应当读作「定义或正面规制**候选**边」，
   它不是一层干净的定义事实；下游图路只拿到 0.442 的单跳召回，与这 37% 的噪声是一致的。**
   若要把它变成干净的定义层，正确做法是拿盲判结果**过滤**（预计剩 ~490 条，`≥800` 会不达标），
   而不是放宽规则把数字凑够——这条留作已知局限，不粉饰。
4. **条文层必要性 52/60 达标（≥50）但仍 8 条未过**：g26/g36/g43/g45/g46/g47/g55/g56，
   原因分三类（概念链不成立 / 特别法优先 / 条文与问句差半句），已在 §4 逐条写明；
   概念层 149/150（仅 g60 的 agency/apparent_agency 未过）。路径断点 0（P3 扩词典前后都复验过）。
5. **κ 不是双人盲标**：Pass A 是人给定的场景+概念链，Pass B 是 LLM 独立判读；κ 衡量「人定骨架 vs 模型判读」，
   不等于标注者间一致性。另：条文选择用了精排模型，Pass B 与它有相关性，κ 会被抬高，**不能当作独立验证**。
6. **5% 二元组泄漏率口径不可达**：题面必然复用法条术语（中位 10%）；验收改用「最长连续公共子串 <10 字」，
   并同时把二元组数据留在 `gold.json` 里，避免口径切换被误读成达标。
7. **概念层人工边的循环性风险**：全图 `manual` 边共 **577 条**（APPLIES_TO 198 + REQUIRES 196 +
   SPECIAL_OF 183），即**概念层是 100% 人工编写**，DEFINES/REFERS_TO 才是规则抽取（另补 5 条 manual 边）。
   其中**最后 35 条 REQUIRES 是为修通金标路径追加的**（如 `non_compete_compensation → liquidated_damages`），
   已从「直接改 data/lexicon/requires.jsonl」改为写进种子 `GOLD_PATH_REQUIRES`，否则重建术语库会丢；
   有 4 条链路同时复核调整过，这属于「按验收结果修数据」，有循环论证风险，已在此披露。
8. **Neo4j 只在单机 Docker 上验过**：本机 Docker Desktop 起 `neo4j:5.26-community`，完成 1799 节点 /
   5697 关系导入，3 条 Cypher 真跑出结果（`data/eval_out/neo4j_cypher_runs.json`）；
   未做集群、未压测并发，评测本身走 NetworkX 镜像以保持可复现。
9. **金标条文仍有选错的历史痕迹，但已修正 28 条**：`ARTICLE_OVERRIDES` 逐条写理由（如 `g28` 违约损失→第五八四条、
   `g51` 劳动合同成立→劳动合同法第十六条）；剩余失败项（`g45` 押金建模成定金等）已进 `UNRESOLVED`，
   承认概念链本身不成立，而不是靠调题面掩盖。
10. **`cite_precision` 有天花板效应**（见 §14）：金标平均只要求 2.02 条引用，而答案平均引 5.5–6.1 条，
    指标对"多引"惩罚极重，理论上限 ≈0.37。它能量化"本地更爱多引"，但**不能区分"引错"与"引多"**；
    正确做法是拆成 `precision@must-cite` 与 `超额引用数` 两个量，本轮未做。

## 14. 本地模型 vs API 后端（A6 实测）

训练侧（LoRA SFT → badcase 补数据 → 重训）与应用侧（本仓库）原本是两个不相干的仓。
这一节把它们接上：**把 A3 数据闭环的最终 adapter 合并进 Qwen2.5-1.5B，量化成 q4_K_M，
用 `LLM_BASE_URL` 换成 OpenAI 兼容端点，在同一批 60 条金标上跟 DeepSeek 做配对对照。**

> 换后端只有三个环境变量，代码零改动：
> ```bash
> LLM_BASE_URL=http://127.0.0.1:11434/v1
> LLM_MODEL=qwen25-1.5b-triple:q4km
> LLM_API_KEY=ollama          # 本地端点不校验，但必须非空，否则 config 判 llm_enabled=False 直接降级
> ```

**C 档 × 60 条金标，同一份检索缓存（三臂配对，bootstrap 2000 次）**

| 指标 | 本地 LoRA 1.5B q4 | 本地基座 1.5B q4 | DeepSeek-chat |
|---|---|---|---|
| cite_precision | 29.1% | 26.0% | **33.6%** |
| cite_recall | 72.8% | 73.3% | 73.3% |
| grounded | 58.3% | 48.3% | **61.7%** |
| 五闸全过 | 58.3% | 48.3% | 61.7% |
| token / 题 | 1343 | 1369 | **1113** |
| 中位延迟 | 5.1 s | 5.5 s | **3.7 s** |
| 每千次成本 | **¥0.10** | ¥0.10 | ¥1.42 |

**结论（三条，都可复算）**

1. **精度：检索覆盖不吃亏，引用精度吃亏。** cite_recall 三臂同分（检索是同一份）；cite_precision 本地 LoRA
   比 DeepSeek 低 **4.5pt（95%CI [−8.7, −0.6]pt，显著）**。差距集中在 three_hop（0.341 vs 0.410）。
2. **微调在应用层是有效的，但补不上容量差。** 同规模基座 vs LoRA：cite_precision **+3.1pt（显著）**、
   grounded **+10.0pt**、cite_p ≥ 50% 的题数 **7 : 1（McNemar p=0.070）**。
   基座对 DeepSeek 是 p=0.0225 的明显劣势，LoRA 对 DeepSeek 是 p=0.51 的"看不出差别"——
   **adapter 把 1.5B 从"明显不如 API"拉到了"差距在噪声里"。**
3. **成本 14.5× 便宜，延迟反而更慢。** 本地每千次 ¥0.098（仅电费；按 3 年折旧摊算是 ¥0.41，仍便宜 3.5×），
   DeepSeek ¥1.418。但本地中位延迟 5.1 s 比 API 慢 1.4 s（显著）。

**一个要说清的指标口径**：金标平均只要求 2.02 条引用，而三臂答案平均引 5.5 / 6.1 / 5.7 条，
`cite_precision = 命中 ÷ 引用` 对"多引"惩罚极重，理论上限只有 ≈0.37（实测 0.291 / 0.336）。
所以这个指标能证明"本地更爱多引"，但不能区分"引错"与"引多"——拆分指标列在 §12 局限第 10 条。

**护栏的价值在这里被量化了**：repair 触发率 DeepSeek 46.7%、本地 LoRA 95.0%、本地基座 100%。
小模型的越界引用不是偶发而是默认行为，没有 `cite_in_retrieval` 这道闸，本地后端上线第一天就会给出凭空条号。

> `tokenizer_config.json` 丢 `chat_template` 导致模板退化成裸拼接）在实验仓库
